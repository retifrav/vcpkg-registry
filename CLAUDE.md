# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal vcpkg git registry (`retifrav/vcpkg-registry`), consumed through a `vcpkg-configuration.json` that pins a `baseline` commit. Many ports started from Microsoft's, but they deliberately differ in patching, package and target names and header paths, so a Microsoft port is a reference for upstream build quirks, never a drop-in replacement or the source of truth for what consumers here link against.

- `ports/<name>/`: `portfile.cmake`, `vcpkg.json`, patches, optional `usage` and `_notes.md`
- `versions/baseline.json` and `versions/<first-letter>-/<name>.json`: the version database, see below
- `triplets/decovar-*.cmake`: overlay triplets (Windows v141–v145 and ClangCL, iOS/macOS fat, Emscripten) that chainload `toolchains/*.cmake` via `${CMAKE_CURRENT_LIST_DIR}/../toolchains/`, so the two folders only work side by side
- `scripts/`: maintenance tools, documented in `scripts/README.md`; `scripts/boost/` generates the Boost ports
- `tests/<name>/`: consumer projects exercising ports; `examples/` are demos for the blog article linked from `README.md`, not tests

`README.md` and `scripts/README.md` keep a `<!-- MarkdownTOC -->` list that is not generated here, so update it by hand when adding or renaming a heading.

## Port conventions

- Sources come from `vcpkg_from_git` with a full 40-character commit hash as `REF` (no `vcpkg_from_github`, no tags). GitHub upstreams use the SSH form `git@github.com:<org>/<repo>.git` in every port; other hosts (googlesource, freedesktop GitLab, SourceForge) use HTTPS.
- The typical patch (`001-single-target-and-installation.patch`, `001-dependencies-and-installation.patch` and the like) replaces upstream's targets with exactly one library whose type follows `VCPKG_LIBRARY_LINKAGE`, and replaces upstream's installation with the shared `Installing.cmake` + `Config.cmake.in` from the host port `decovar-vcpkg-cmake`, which `portfile.cmake` copies into the source tree (a port with special needs ships its own `Config.cmake.in` instead). `Installing.cmake` puts public headers into `include/<name>/` and namespaces the exported target when the patch sets `PROJECT_NAMESPACE_FOR_PACKAGE`. `ports/zlib/_notes.md` lists every property such a patch has to keep across rebases, and is the model to follow.
- Dependencies are found in CONFIG mode and linked by this registry's own target names (`sqlite::sqlite3`, `zlib::zlib`, not CMake's `SQLite::SQLite3`/`ZLIB::ZLIB`). Changing a port's exported package or target name therefore means updating the patches of its dependents (`rg -l '"name": "<port>"' ports/*/vcpkg.json`).
- OpenSSL is no exception, although CMake ships a find module for it and the targets keep their `OpenSSL::SSL`/`OpenSSL::Crypto` names: a port looks for it with `find_package(OpenSSL CONFIG REQUIRED)`, and its installed config with `find_dependency(OpenSSL CONFIG REQUIRED)`. The plain form runs `FindOpenSSL.cmake` directly and never reads the port's config, so a consumer without the vcpkg toolchain links the release libraries in Debug (see `ports/openssl/_notes.md`). The lookup is there only when a port builds with OpenSSL: `cpp-http` has it under its `openssl` feature, and without that feature its installed config has none. Two plain lookups are left as they are, by the user's choice on 2026-11-26: `boost-mysql` (written into its config by `BoostInstall.cmake` from `boost-cmake`) and `aws-sdk-cpp` (its CRT submodule `aws-c-cal`, Linux only).
- No port calls `vcpkg_copy_pdbs()`: PDB files are of no interest in this registry. Don't add it to a new port, don't take it over when syncing a port with microsoft/vcpkg (nearly every port there has it), and don't restore it where it is missing.
- New patches are named `NNN-description.patch`; older ports still have unnumbered ones, renamed when the port is reworked anyway (as `xxhash` 0.8.4 did). vcpkg applies patches with `git apply --ignore-whitespace`, so check them the same way.
- `_notes.md` holds maintainer notes, often with items to re-check on every update (a workaround to drop once upstream fixes it, an upstream option list to compare). Read it before updating or patching that port and keep it current. It sits inside the port folder, so editing it changes the port's `git-tree` like any other file.
- `vcpkg.json` may use only the `version` scheme (strict `X.Y.Z`, no leading zeros) or `version-date`; upstream versions with fewer components are padded with `0` (zlib `v1.4` → `1.4.0`). `license` is an SPDX expression; dependency minimums use `version>=`.
- Files headed `# Automatically generated by scripts/boost/generate-ports.ps1` (the `boost-*` ports) are regenerated by that script (`pwsh` is in the image), not hand-edited. `ports/boost` is not one of them: it is a hand-made Windows-only port for prebuilt binaries.

## wolfSSL and curl

**Before changing the `wolfssl` or `curl` port, or chasing failures in `tests/curl/test-curl-tool.sh`, read `.claude/notes/wolfssl-curl-tls.md`.**

- A new wolfSSL define goes in as a CMake option if one exists, otherwise into `WOLFSSL_DEFINES_WITHOUT_OPTION` in the portfile. Never pass it as a raw C flag alone: flags don't reach the generated `wolfssl/options.h`, so consumers would compile against a different configuration than the library.
- On a wolfSSL update, diff the `add_option` defaults in its `CMakeLists.txt` against the previous version. The option descriptions are not reliable about defaults.
- badssl.com randomly resets any connection whose ClientHello spans more than one TCP segment, and with a post-quantum key share both back ends send about 1.5 KB. `badssl()` in the test script repeats those requests, so a reset there is never a reason to make the ClientHello smaller in a port.
- In the `wolfssl` port `WOLFSSL_MLKEM` and `WOLFSSL_CURVE25519` are unconditional and belong together, so don't turn either back into a feature. Without Curve25519 every server answers the ML-KEM key share with a HelloRetryRequest, and there is no post-quantum key exchange at all.

## Versions database

**Before running `add-new-version.py` or replacing a `git-tree` in place, read `.claude/notes/version-bookkeeping.md`.**

`scripts/check-versions-and-hashes.py` compares every manifest version against `versions/` and every `git-tree` against `git rev-parse HEAD:ports/<name>`, so it judges *committed* state. Every commit that touches `ports/<name>/` has to carry that port's matching `git-tree` too, otherwise consumers pinned to that commit build stale port files or fail to fetch the tree.

- New version: prepend an entry to `versions/<c>-/<name>.json` and update `versions/baseline.json`.
- Fix to an already pushed version (its commit is in `origin/master`, check with `git merge-base --is-ancestor <sha> origin/master`; the container cannot fetch, so that ref is as of the user's last host-side push or fetch): bump `port-version` and add a new entry.
- Fix to a version that is not pushed yet: replace its `git-tree` in place (as `ac856c6` did for curl 8.23.0). Doing that to a pushed version is the user's call, never a default.
- A baseline behind its manifest can be intentional (a version held back from the baseline); the checker lists those separately, and they are not failures.
- `baseline.json` is alphabetical; insert new entries in place.

`scripts/add-new-version.py --port-name X --port-version 1.2.3#4` writes both files in the house JSON format (4 spaces, opening braces on their own line). Before running it:

- It gets the `git-tree` of uncommitted changes by running `git add ports/X`, `git write-tree --prefix`, then `git reset ports/X` in the real index, which also unstages anything already staged there. Run it on a copy of the index: `cp .git/index <scratch>/index && GIT_INDEX_FILE=<scratch>/index python3 -I ./scripts/add-new-version.py …`, then delete the copy. For an in-place replacement, get the hash the same way: `GIT_INDEX_FILE=<copy> git add ports/X && GIT_INDEX_FILE=<copy> git write-tree --prefix=ports/X`.
- The `#N` suffix is mandatory, also for a plain new version: `3.6.5#0`, since a bare `3.6.5` is rejected with `incorrect port version format`.
- It cannot add a port that is missing from the baseline (exit code 9). For a new port, add the baseline entry by hand and run it with `--not-updating-baseline`, which still creates the versions file.
- `scripts/vcpkg-tools.json` (an empty tool list) exists so that `vcpkg x-add-version --vcpkg-root .` works as well; keep it.

## Commands

Python is externally managed in the container, so run the scripts with `uv` rather than the `pip install` from `scripts/README.md` (the packages are in the uv cache; the checker takes about 5 seconds):

```sh
uv run --no-project --with pandas --with pandera --with tabulate --with colorama python -I scripts/check-versions-and-hashes.py   # exit 1 lists the problematic ports
uv run --no-project --with license-expression python -I scripts/license-based-todos.py
python3 -I scripts/add-new-version.py --help   # stdlib only
```

`ruff check scripts/` picks up `ruff.toml` (Python 3.12 minimum). The older scripts are not ruff-clean (79 findings as of 2026-11-16, mostly typing-style `UP006`/`UP045`) and were never `ruff format`-ted, so judge a change by not adding findings, and don't reformat.

### Building a port from the working tree

**Before building a port here, read `.claude/notes/building-in-the-container.md`**: it covers how to find the orgs to rewrite and what cannot be built.

Classic mode with the whole `ports/` as overlay builds the working tree without involving the registry remote (verified with `xxhash[tool]` on x64-linux, 2026-11-16). Use `x64-linux` or `arm64-linux` according to `uname -m`:

```sh
vcpkg install '<port>[<features>]' --classic --binarysource=clear --overlay-ports=/workspace/ports --triplet x64-linux \
    --x-install-root=<scratch>/installed --x-buildtrees-root=<scratch>/buildtrees --x-packages-root=<scratch>/packages
```

Portfiles fetch upstream over SSH, which cannot work in the container. Prefix the command with one scoped `GIT_CONFIG_KEY_n='url.https://github.com/<org>/.insteadOf'` / `GIT_CONFIG_VALUE_n='git@github.com:<org>/'` pair per upstream org of the port and its dependencies, with `GIT_CONFIG_COUNT` to match. Never use a blanket `git@github.com:` rewrite (see the global `CLAUDE.md`). A `REF` fetched before is cached as a tarball in `~/.cache/vcpkg/downloads/` and needs no rewrite. Consume the result from a scratch project with `-DCMAKE_PREFIX_PATH=<scratch>/installed/<triplet>`. `boringssl` cannot be built here.

### Tests

`tests/<name>/` share `tests/_common/CMakePresets.json` and `tests/_common/vcpkg-configuration.json` through symlinks. `cmake --preset vcpkg-default-triplet && cmake --build --preset vcpkg-default-triplet` configures, builds and installs into `install/<preset>/`. That configuration pins the registry to a pushed `baseline` over SSH, so these projects test the registry as of that commit, not the working tree; the baseline there gets bumped (`Tests: Updated baseline`) when they should pick up newer ports.

`tests/curl/test-curl-tool.sh -c <path-to-curl-tool>` checks a `curl[tool]` build against public services; it needs network access, and a single failing check should be re-run before blaming curl.

## Commits

The user makes the commits, so leave changes in the working tree and propose subjects in the repository's format:

- `[name] new port`, `[name] version X.Y.Z`
- `[name][X.Y.Z] <what changed>` for a change within a version, `[name][X.Y.Z] port version N` when that change bumps `port-version`, `[name][X.Y.Z][N] <what changed>` for a further change to port-version N
- `Scripts: …`, `Tests: …`, `README: …` for everything else
