# Maintainer notes

## Sources

The sources come from the release tarball, not from Git. The repository does not contain `src/glew.c` and `include/GL/*.h`: they are generated by `make extensions` (*GNU make, Perl and Python*), which clones `KhronosGroup/OpenGL-Registry`, `KhronosGroup/EGL-Registry` and `nigels-com/glfixes` with `--depth=1` at whatever their HEAD is, so the result is not reproducible. Upstream's README itself recommends building from a tgz/zip release snapshot. Still true as of `glew-2.3.1` (*commit `f5920a565fca1b49b2a5e213b95f7e403a369505`*); on every update check whether the tag has them now: `git ls-tree -r --name-only <tag> -- src/glew.c include/GL/glew.h`.

The second URL is a mirror on `files.decovar.dev`, which does not update itself: upload the new tarball there on every update.

## Patch

`001-single-target-and-installation.patch` patches only `build/cmake/CMakeLists.txt`, replacing the upstream `glew` (*shared*) and `glew_s` (*static*) targets and their installation with one target. It has to keep these properties when it is rebased onto a new upstream version:

- `cmake_minimum_required` is raised from upstream's `3.16` to `3.28`
- one library type per build, chosen by `BUILD_SHARED_LIBS`: the shared variant gets `GLEW_BUILD`, `VERSION`/`SOVERSION` and `PREFIX ${DLL_PREFIX}`, the static one gets `GLEW_STATIC` (*`PRIVATE` and `INTERFACE`*) and `PREFIX lib`
- the binaries are named as upstream names them: `OUTPUT_NAME ${GLEW_LIB_NAME}` (*`GLEW`, or `glew32` on Windows*) with upstream's `d` debug postfix, so `libGLEW.so`/`libGLEW.a` and `libGLEWd.so`/`libGLEWd.a` on Linux, `glew32.dll`/`glew32.lib` and static `libglew32.lib` on Windows
- the target is called `glew` and is exported as the lower-case namespaced `glew::glew` (*no `EXPORT_NAME`, `PROJECT_NAMESPACE_FOR_PACKAGE` set to `glew`*), with the CMake package config in `share/glew/`, installed by the common `Installing.cmake` from `decovar-vcpkg-cmake` and the port's own `Config.cmake.in`, which differs from the common one only by `find_dependency(OpenGL)`. Upstream's `GLEW::glew`/`GLEW::glew_s` and its `GLEW::GLEW` (*which CMake's `FindGLEW` creates too*) are deliberately not provided, so consumers written against those have to switch to `glew::glew`
- the public headers (*`glew.h`, `glxew.h`, `wglew.h`, `eglew.h`*) are installed into `include/GL/` (*`PROJECT_INCLUDES_NAME_FOR_PACKAGE` set to `GL`*), so consumers include them as `<GL/glew.h>`, as with every other GLEW distribution
- `PROJECT_VERSION` is set from `GLEW_VERSION` before including `Installing.cmake`, because upstream's `project()` has no version (*it is parsed from `config/version` after it*), and without it there would be no `glewConfigVersion.cmake`
- with MSVC the `-nodefaultlib -noentry libvcruntime.lib msvcrt.lib` link options are removed (*Microsoft's port does the same in `fix-LNK2019.patch`*), while `-GS-`, the `/RTC` removal and the x86-only `-BASE:0x62AA0000` (*now only for the shared variant*) stay as upstream has them
- the library links the imported `OpenGL::GL` target instead of upstream's library paths, so the exported `glewTargets.cmake` has no paths from the build machine in it (*2.2.0 had `/usr/lib/libGL.so;/usr/lib/libGLU.so;/usr/lib/libSM.so;/usr/lib/libICE.so;/usr/lib/libX11.so;/usr/lib/libXext.so` there*), and consumers resolve it with their own `find_package(OpenGL)`, which `Config.cmake.in` does with `find_dependency(OpenGL)`. With GLVND `OpenGL::GL` links `OpenGL::OpenGL` and `OpenGL::GLX`. It has to stay in the link interface, because `glew.h` declares the GL 1.1 functions for direct linking
- the X11 libraries are not linked: the library calls only GLX functions (*`glXGetProcAddressARB`, `glXQueryVersion` and `glXGetClientString`, checked with `nm -u` on 2.3.1*), and only the X11 headers are needed, because `GL/glxew.h` includes `X11/Xlib.h`, so `find_package(X11)` stays for `X11_INCLUDE_DIR`. Consumers that call Xlib themselves have to link X11 themselves
- the `GLEW_EGL`, `GLEW_OSMESA` and `GLEW_REGAL` branches still add upstream's library paths/names, which is fine as long as the port enables none of these modes

Not installed: `glew.pc`, the PDB, upstream's `glew-config.cmake` and `CopyImportedTargetProperties.cmake`. The `BUILD_UTILS` executables still build against the single target, but the port builds with `BUILD_UTILS=0`.

The package is meant to be found only with `find_package(glew CONFIG REQUIRED)` (*`NO_MODULE` instead of `CONFIG`, a version and `QUIET` instead of `REQUIRED` are fine too*), and `vcpkg-cmake-wrapper.cmake` refuses everything else with a `FATAL_ERROR`, because vcpkg runs that wrapper for every spelling of the name (*it looks it up by the lower-cased name*). Any other spelling, such as `find_package(GLEW)`, would go to CMake's own `FindGLEW` module, which the port does not control: on Linux with a static triplet it fails (*it looks only for shared libraries unless `GLEW_USE_STATIC_LIBS` is set*), and with a dynamic one it finds `libGLEW.so` by itself and creates its own `GLEW::glew`/`GLEW::GLEW` (*checked on 2026-11-16 with CMake 3.31*). Module mode is refused too, because `Findglew.cmake` can resolve to `FindGLEW.cmake` on case-insensitive file systems. This works only for projects using the vcpkg toolchain; without it, the wrapper isn't run at all. It also means that a third-party package config calling `find_dependency(GLEW)` fails against this port.

On every update diff `build/cmake/CMakeLists.txt` against the previous version before rebasing the patch.

## GLU

GLEW does not link GLU, and that is deliberate. The library itself does not use it (*it is built with `GLEW_NO_GLU`*), and GLU is a system library everywhere (*`glu32` from the Windows SDK, the OpenGL framework on Mac OS, `libGLU` from the distribution on Linux*), so consumers that call GLU functions link it themselves, for example with `${OPENGL_glu_LIBRARY}` after `find_package(OpenGL)`. Until 2.2.0 GLEW linked `${OPENGL_LIBRARIES}`, which FindOpenGL fills with GLU too, but only when GLU happened to be found at build time; 2.3.0 switched to GL/GLVND and GLX only, and `gource` and `logstalgia` got `${OPENGL_glu_LIBRARY}` in port version 2 because of that.

`glew.h` still includes `<GL/glu.h>` (*unless the consumer defines `GLEW_NO_GLU`*), so the GLU headers are needed for compiling against GLEW. Microsoft's port burns `GLEW_NO_GLU` into `glew.h`; this one must not, because `gource` and `logstalgia` get `<GL/glu.h>` through `<GL/glew.h>`.

## Emscripten

The port passes `GLEW_X11=0` for Emscripten (*the option exists since 2.3.0*). That has not been build-tested.
